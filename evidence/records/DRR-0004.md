## Decision

- **Authority level:** B (release policy — decides when a public stability
  commitment is made)
- **Guard rails / invariants implicated:** roadmap honesty rule (§6: docs do
  not promise what tests do not observe), upgrades.md §1 (pre-1.0 = no
  stability guarantee beyond the API contract; the contract IS the
  compatibility surface), evidence rule (§6: performance/scale claims ship
  with reproducible results), api-contract as the single caller-visible
  surface
- **Requester:** maintainer (asked for a recommendation during the Phase 0
  exit audit)
- **Date opened:** 2026-09-26
- **Status:** applied (criteria recorded; first evaluation at Phase 1 exit)

## Context

The repo tags v0.2.0…v0.5.4 under the pre-1.0 policy: v0.x minors may break
anything except what api-contract.md promises. Tagging v1.0.0 flips the
default — breaking changes become 2.0-only (semver). The roadmap has five
phases; the natural pressure is "when do we call it 1.0?" The wrong answer
either over-promises (1.0 before the contract is test-enforced) or
under-delays (waiting for features the contract already disclaims as absent).

## Options considered

| Option | Meaning | Trade-offs |
|---|---|---|
| 1. Phase 1 + burn-in (strict) | Tag after the Migration phase exit (migration CLI, verification report, compatibility suite, playbook, endpoint reference) AND a burn-in of ≥ 4–6 weeks / ≥ 2 tagged releases with zero contract-breaking changes | The compatibility suite turns the contract from a document into an enforced promise — the same "claim must be observed" logic that drove the pg-matrix job (DRR-0003). Burn-in proves the promise under real use before it is public. Cost: 1.0 arrives later |
| 2. Early (right after Phase 1 code) | Tag as soon as Phase 1 merges | Skips evidence that the promise holds across time; a breaking change right after 1.0 would make semver meaningless |
| 3. Conservative (after Phase 4) | Wait for multi-instance scale, retention, distributed limits | Contradicts the contract's own §10 "not in this contract yet" honesty — those are documented absences, not 1.0 blockers; delays the stability signal by the longest phase |

## Recommendation

Option 1 (confirmed by maintainer 2026-09-26). **v1.0.0 is tagged when ALL
criteria below hold** — first evaluation point: Phase 1 exit.

1. **Phase 1 exit met:** a real PocketBase application moved to PG-BASE
   end-to-end, repeatably, verified (roadmap Phase 1 exit), via the
   migration CLI + verification report + playbook.
2. **Compatibility suite green:** checklist §3 rows satisfied against our
   own contract, including JS and Dart SDK paths — the contract is enforced
   by tests, not just documented.
3. **Release checklist green at tag time:** checklist §6 fully green on the
   1.0 tag run (including security scan and both pg-matrix legs).
4. **Burn-in:** ≥ 4–6 weeks and ≥ 2 tagged releases after criterion 1 with
   zero contract-breaking changes (any breaking change restarts the clock).
5. **Upgrade path exercised in real use:** at least one app upgrade and one
   restore-based rollback executed outside the test suite (production
   instance or maintainer-owned deployment), feeding `last_verified_backup`.
6. **Security posture current:** govulncheck + npm audit + gitleaks green at
   tag time; SECURITY.md supported-versions table updated to add v1.0.x.
7. **Release artifacts:** CHANGELOG top section `## v1.0.0` states the first
   stable release and the forward semver commitment (breaking changes only
   in 2.0); docs/upgrade policy updated from "pre-1.0" language to the 1.0
   stance.

**Explicitly NOT 1.0 blockers** (ship as 1.x minors): Phase 2 vector/search,
Phase 3 MCP server, Phase 4 multi-instance scale-out, request-log retention,
GIN filter indexes — api-contract §10 already declares these absent, so
their absence is honest at 1.0.

## Risks / reversibility

- **Tagging too early:** a breaking change after 1.0 forces a 2.0 or a
  silent contract violation — mitigation: criteria 2 + 4 make the promise
  test-enforced and time-proven.
- **Tagging too late:** staying on 0.x signals instability longer than
  needed — mitigation: criteria are a checklist, not a date; if Phase 1
  exit + burn-in are met, do not invent extra gates.
- **Reversibility:** a 1.0 tag is public and effectively irreversible;
  pre-tag, any criterion can be revised by a new DRR (superseding this one).
