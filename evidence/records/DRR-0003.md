## Context

Phase 0's last tracked roadmap item — "Versioning and upgrade policy" — bundles two deliverables: a documented policy for how PG-BASE versions break and how an operator rolls back an app or a PostgreSQL upgrade, and a PostgreSQL 16/17 CI matrix so that the supported-engine claim is observed rather than asserted. CI today runs the whole suite against a single hardcoded `postgres:16-alpine`; the README claims "PostgreSQL 16+" with no observation of 17.

## Options considered

| Dimension | Option | Trade-offs |
|---|---|---|
| Matrix shape | 1. Dedicated `pg-matrix` job, `matrix.pg: [16, 17]` | Explicit and self-contained; both legs visible in one job; extendable (18 later) at the cost of duplicating the 16 leg already covered by `goreleaser`/`race` (parallel — no wall-clock penalty) |
| | 2. Extra 17-only job | Cheapest; the claim is implicit — swapping the main job's image later would silently break it |
| | 3. Refactor the `goreleaser` job into a matrix | No duplication, but couples the release/build path with the compatibility matrix and requires splitting build from test — largest workflow refactor |
| Policy location | 1. New `docs/deployment/upgrades.md` | One topic, one page (house style: production, DR, single-host are separate pages); production.md stays focused on go-live |
| | 2. New section in `production.md` | Fewer files, but overloads an already long runbook and buries rollback next to first-run content |
| Stance | 1. Honest & minimal | Pre-1.0: no stability guarantee beyond the API contract (which is the compatibility surface, per contract rule); forward-only migrations ⇒ rollback = restore the pre-upgrade verified backup with the old binary; PostgreSQL upgrades operator-owned; supported set = 16/17 observed in CI |
| | 2. Plus hard semver-v1 + security backport SLA | Stronger promise than the repo currently evidences; couples this PR to future release-engineering commitments |

## Recommendation

Option 1 in every dimension (confirmed by maintainer 2026-09-26):

- **CI:** dedicated `pg-matrix` job with `strategy.matrix.pg: [16, 17]`, `fail-fast: false`
  (both legs must report — the matrix *is* the evidence), running the same plain full
  suite as the other jobs. `TEST_POSTGRES_IMAGE` overrides the compose image per leg; the
  compose default stays `postgres:16-alpine`, so `make test` and local development are
  unchanged. Each leg installs the matching `postgresql-client-<major>` so
  `pg_dump` ≥ server major holds for the backup round-trip test. `race` stays on 16 (race
  coverage is about the Go code, not engine coverage — rationale in the workflow comment).
  The `docker` job's `needs` gains `pg-matrix`: an image publishes only after both engine
  legs are green.
- **Docs:** new operator page `docs/deployment/upgrades.md` (sidebar in both nav copies),
  stance 1: honest & minimal — pre-1.0 contract-surface policy, restore-based app
  rollback, operator-owned PostgreSQL upgrade, supported set observed by `pg-matrix` §4
  table. Cross-links: production §3, disaster-recovery intro, developing §10 (local leg
  reproduction).

## Risks / reversibility

- **Blast radius:** CI + documentation only — zero Go code changes. One extra CI job (two
  legs, plain suite, parallel to existing jobs; ~2× runner minutes on the plain pass, no
  wall-clock impact on the existing jobs). Release path waits on the new legs via
  `docker.needs`.
- **Reversibility:** fully reversible — revert the 12 files; the compose default means
  local workflows never depended on the override.
- **Rollback:** revert the commit; no migrations, data, or caller-visible API behavior
  involved (api-contract §10 only removed a not-yet-available clause from the
  do-not-assume list).
- **Evidence of success:** local leg 17 (`postgres (PostgreSQL) 17.11`): full suite
  `-v` → 0 FAIL / 35 packages ok / §6 gate = 1 (only sanctioned `test_recover`) /
  `TestPGDumpExportImportRoundTrip` PASS (not skipped); local leg 16 (default image
  restored): identical 0 FAIL / 35 ok / gate = 1 / round-trip PASS;
  `make docs-check` + `docs:build` green; `golangci-lint` 0 issues; final confirmation is
  the `pg-matrix (16)` / `pg-matrix (17)` legs green on the PR's own CI run.
