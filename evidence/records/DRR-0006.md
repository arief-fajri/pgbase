## Context

W-01 (`docs/contributor/methodology/failure-modes.md`): `apis/realtime.go` `OnModelDelete` (pre-commit, Priority 99) calls `publishRealtimeEvent(delete)` — the outbox INSERT for a delete is written before the delete transaction commits. A delete that later fails still notifies peers (cross-instance) of state that never happened. Local SSE fanout is already split correctly (dry-cache pre-commit, broadcast on `OnModelAfterDeleteSuccess`, cleanup on `OnModelAfterDeleteError`); only the outbox publish is mis-ordered.

DRR-0005 orders this fix **before** the Phase 1 compatibility suite freezes: a suite built against current behavior would codify the bug into our own contract, making the later fix a breaking change.

## Options considered

| Option | Trade-offs |
|---|---|
| 1. Move outbox publish to `OnModelAfterDeleteSuccess`, snapshot stashed pre-commit (recommended) | Post-commit publish sees only committed state; snapshot captured pre-commit (record gone after delete, custom models unresolvable post-delete). Needs a small in-memory stash keyed by dry-cache key, cleaned on success + error. No schema/DLL change, no new route |
| 2. Keep pre-commit publish, compensate with a "delete-cancelled" event on error | Doubles the protocol, requires receivers to handle retraction, still exposes a transient false event; more contract surface, harder suite |
| 3. Wrap outbox INSERT in the same DB tx and rely on rollback | Outbox INSERT via `NonconcurrentDB()` is not guaranteed to join the record delete tx (hook app context differs); ordering would stay implicit and untestable |

## Recommendation

Option 1. Semantics written into the contract in the same change:

- Delete events (local + outbox) are emitted **only after the delete commits**.
- Delivery stays **at-most-once** (existing W-02 scope unchanged): no replay across restarts, slow consumers dropped not backpressured.
- Delete snapshot is captured pre-commit and replayed verbatim (sanitized: no `password`/`tokenKey`).

## Risks / reversibility

- **Stash leak:** entries keyed by dry-cache key (`action/table/pk`); cleaned on both `AfterDeleteSuccess` and `AfterDeleteError`. A hook that never fires would leak one small entry — same lifecycle as the existing dry-cache messages, which have the identical guarantee.
- **Custom models:** resolved post-delete via collection only (existing pattern); snapshot comes from the stash, so custom-model deletes keep working.
- **Reversibility:** hook reordering only; no migration, no route change. Rollback = revert commit.
- **Evidence:** regression test (failing delete → 0 outbox rows; success → 1 row with snapshot) + contract diff.
