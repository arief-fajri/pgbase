# DRR-0000 — Gate GHCR `:latest` on quality gates and publish event

## Decision

- **Authority level:** B2
- **Guard rails / invariants implicated:** G-CI-01 (new), G-REL-06
- **Requester:** agent (opencode)
- **Date opened:** 2026-09-17
- **Status:** confirmed by maintainer

## Context

GHCR `:latest` tag was moved immediately on `v*` tag push, in parallel with
the test/race/lint jobs.  A user running `docker compose -f deploy/docker-compose.quickstart.yml`
or `curl | sh` (quickstart) would pull an image that had not yet passed
quality gates.  The draft GitHub release mechanism was correct, but the
Docker image tag lacked equivalent enforcement.

## Options considered

| Option | Trade-offs |
|---|---|
| 1. Add `needs: [goreleaser, race, lint]` to the `docker` job in `release.yaml`; stop pushing `:latest` on tag; promote via `release: [published]` event. | Clean separation; `:latest` always == last published release; immutable tag still pushed during build. |
| 2. Same as 1 but skip the immutable tag entirely; build fresh on publish event. | Deterministic but slower; loses traceability of which commit produced `:vX.Y.Z`. |
| 3. Keep current behavior; add a warning comment only. | Minimal change, but `:latest` still unvalidated — guardrail gap remains. |

## Recommendation

Option 1.  Gate the `docker` job on all three quality jobs; remove `:latest`
from the tag-push step; add `docker-latest.yaml` that re-tags the immutable
image as `:latest` when the draft release is published.

## Risks / reversibility

- **Blast radius:** any workflow YAML error can block the release pipeline.
  Mitigated by `actionlint` verification before merge.
- **Reversibility:** fully reversible — revert the two workflow files and the
  docs edits.
- **Rollback:** delete the commit; no data or schema changes involved.
- **Evidence of success:** `actionlint` passes; manual `workflow_dispatch` on
  an existing published tag validates the promote logic.
