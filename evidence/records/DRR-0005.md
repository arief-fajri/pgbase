## Context

An external roadmap review proposed reordering the roadmap around production validation. Before adoption, its claims were verified against the tree (not against the roadmap's own inventory): the review was accurate — production primitives exist and are largely tested, but the evidence layer is missing (zero load benchmarks, zero numeric SLOs, compatibility suite 0/12 per checklists §3, S3 never exercised against a real provider, the audit partition cron untested). The goal of this repository is stability and production-worthiness per the positioning, which reorders the question from "which features next" to "what must be proven before stability claims".

## Options considered

| Option | Trade-offs |
|---|---|
| 1. Keep the current order (vector at Phase 2, MCP at Phase 3, scale at Phase 4) | Growth bet — differentiators attract attention. Contradicts §0 "not a Supabase clone" (vector is Supabase's mindshare), defers known correctness bugs (W-01/W-02) and unbounded-growth risks (W-09) behind features |
| 2. Adopt the review as-is (validation as a sequential Phase 2) | Correct priorities, internally contradictory (validation is declared a cross-phase gate AND a blocking phase); drops current Phase 4 hygiene items (`_logs` retention, GIN indexes); drops Ecosystem entirely |
| 3. Hybrid — reorder + validation as gate-and-workstream + re-triage | Validation gates every phase exit AND runs as a parallel evidence workstream (starts during Phase 1). Correctness items move before the contract freeze; single-instance hygiene items move out of "Scale" into validation |

## Recommendation

Option 3, applied as:

- **Phase 1 — Migration & Compatibility** gains a realtime-correctness item: close W-01 (delete published pre-commit) and write the realtime delivery semantics (at-most-once vs at-least-once, replay) into the contract **before** the compatibility suite freezes — a suite built against current behavior would codify the bugs into our own contract.
- **Phase 2 — Production Validation & Evidence** (new, parallel workstream): SLO + capacity envelope, load harness, automated failure-injection (PG restart, app crash, network partition, pool exhaustion, reconnect storm), burn-in via dogfooding, concurrency tests; re-triage into this phase: W-09 (audit DEFAULT pruning), `_logs` non-bloating retention, GIN/`jsonb_path_ops` filter indexes, W-16 (resolve or accept with a written decision).
- **Phase 3 — HA & Scale** (was Phase 4): multi-instance topology test, outbox hardening (W-02 replay; default-on decision), distributed rate limiter, DB-LISTEN cache invalidation (W-04), cron guard (W-03), S3 multi-instance files (W-05), PgBouncer validation, replica guidance.
- **Phase 4 — PostgreSQL Advantage** (was Phase 2) and **Phase 5 — Agent Interface & Ecosystem** (was Phase 3 + Phase 5).
- **Amended v1.0.0 gate** (supersedes DRR-0004's "Explicitly NOT 1.0 blockers" clause): v1.0.0 = DRR-0004 criteria 1–7 **plus** Phase 2 evidence **plus** Phase 3 topology evidence. Consequence accepted: v1.0.0 arrives materially later — the HA set is the largest engineering lift in the roadmap.
- Boundaries preserved: HA is guidance + tested topologies, not a failover manager; RPO stays operator-side (backup interval — PG-BASE documents and drills it, it does not own PITR); no platform parity.
- The per-capability evidence base is the Production Readiness Matrix (`docs/contributor/production-readiness.md`), re-audited at every phase exit.

## Risks / reversibility

- **v1.0.0 delay:** the HA lift (distributed limiter, LISTEN invalidation, S3 multi-instance, outbox replay, topology tests) now sits on the critical path — mitigation: the blocker set above is enumerated so the gate stays auditable; dogfooding burn-in runs concurrently with Phase 2 so wall-clock cost is partially absorbed; Phase 4/5 remain explicitly not-blockers.
- **Contract freeze danger:** if W-01 and the realtime semantics land after the compatibility suite is written, the suite freezes the bugs — mitigation: the Phase 1 ordering above.
- **Cross-reference drift:** phase renumbering touches failure-modes.md (W-01…W-05, W-09), observability.md, checklists.md, api-contract.md §10, collections-and-api-rules.md — swept in the same change.
- **Reversibility:** pre-1.0, any criterion here is revisable by a superseding DRR; DRR-0004 remains the base criteria document with its Outcome annotated.
