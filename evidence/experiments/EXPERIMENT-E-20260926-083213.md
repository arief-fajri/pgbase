- **Experiment:** E (backup round-trip + G-REL-04 signal)
- **Date:** 2026-09-26
- **PG-BASE version:** PR-5 commit + PR-6 working tree (restore drills + `last_verified_backup`)
- **PostgreSQL version:** 16.15 (pg_dump/pg_restore 18.3 on PATH)
- **Topology:** single instance; storage local
- **Harness version:** `evidence/experiments/EXPERIMENT-E.sh` (extended in this PR — see below)
- **Verification level:** L2 (re-qualified — the harness changed: post-restore `last_verified_backup` phase)
- **Guard rails exercised:** G-DB-05, G-REL-04 (verified-restore timestamp)
- **Invariants exercised:** I4, I5

## Scenario

Same as the previous runs, plus the G-REL-04 loop: after the destroy+restore,
the verified restore must (a) persist the RFC3339 timestamp to `_params`
(`last_verified_backup`), and (b) expose it as
`pgbase_backup_last_verified_timestamp_seconds` on `/metrics` after a fresh
boot (restore → `_params` row → boot load → gauge).

## Harness changes in this PR

- post-restore phase: read `last_verified_backup` via SQL; boot the app again
  with `PB_METRICS_ADDR=127.0.0.1:8097`; wait on `/api/ready` (readiness, not
  liveness — same switch as the quickstart in the PR-3); scrape `/metrics` and
  assert the gauge > 0; both checks gate the VERDICT
- PRE/POST `_params` counts now exclude the `last_verified_backup` row: the
  verified restore itself writes that row after `pg_restore`, so a plain count
  equality would differ by one
- pre-backup boot wait switched `/api/health` → `/api/ready`

## Results

- backup: rc=**0**, `backups/exp-e.zip` **created**
- restore: rc=**0** (hardened W-08 gate, benign noise tolerated)
- `_collections`: 6 → **6**; `_params` (excl. metadata row): 2 → **2**; probe row: **1**;
  `_superusers`: 1 → **1**; password-hash length: 60 → **60**
- `last_verified_backup`: **2026-09-26T01:32:17Z** (persisted)
- `pgbase_backup_last_verified_timestamp_seconds`: **1.790386337e+09** (> 0 after boot)

## Verdict

**PASS** (L2). The full G-REL-04 loop holds: only a verified restore writes the
timestamp, the timestamp survives the boot, and the gauge exposes it. Failure
paths (rejected restore → no row, unparseable value → 0) are covered by the Go
regression tests (`TestImportFromPGDumpRecordsVerifiedTimestamp`,
`TestBootstrapLoadsLastVerifiedBackup`).
