## Scenario

With a saturated data pool (data pool = 2 for a fast deterministic run), HTTP
requests must not hang unboundedly: they complete with a bounded response
(either an HTTP error or the pool-wait path) and the process must remain
alive. The claim exercised G-DB-01/08.

## Procedure

`bash evidence/experiments/EXPERIMENT-B.sh`

1. Fresh DB `pgbase_exp_b`; schema pre-provisioned with a single `pgbase
   migrate up` run (documented operator path).
2. `pgbase serve --http=127.0.0.1:8098` with `PB_POSTGRES_MAX_OPEN_CONNS=2`.
3. 32 concurrent HTTP probes against `/api/health`; record response codes,
   curl failures, and max response time.
4. Snapshot pool-wait metrics before teardown; verify process alive.

## Results

- requests completed with bounded response: **32/32**
- curl-level failures: **0**
- http codes: 32 × 401 (the probe endpoint requires auth; response bounded)
- max response time: **0.004 s**
- metrics snapshot (pool wait): recorded in log
- app alive after saturation: **yes**
