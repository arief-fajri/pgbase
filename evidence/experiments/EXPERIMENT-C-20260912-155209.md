- **Invariants exercised:** I14

## Scenario

When PostgreSQL blocks an app query behind an ACCESS EXCLUSIVE lock, the
query must respect the (role-level) lock timeout and fail with a bounded
error instead of blocking forever; once the lock is released, the same query
must recover. Proves G-DB-04 (bounded lock waits).

## Procedure

`bash evidence/experiments/EXPERIMENT-C.sh`

1. Fresh DB `pgbase_exp_c`; schema pre-provisioned.
2. `pgbase serve --http=127.0.0.1:8097`; wait for `/api/health` 200.
3. Baseline probe `/api/collections/users/records` (expect 200).
4. External session: `BEGIN; LOCK TABLE users IN ACCESS EXCLUSIVE MODE;
   SELECT pg_sleep(120); COMMIT;` (a stuck external client / DDL).
5. Probe while the lock is held (bounded response expected).
6. Release the lock via `pg_terminate_backend`; probe again (recovery).
7. Verify the app process is still alive.

## Results

- baseline (no lock): http=**200**
- with lock held: http=**400**, elapsed **30 s** (exactly the role-level
  lock_timeout; bounded, not a hang)
- after lock release: http=**200**, elapsed **0 s**
- app alive: **yes**

## Verdict L3: **PASS** — regenerate raw stdout via `bash evidence/experiments/EXPERIMENT-C.sh` (tee'd to `evidence/experiments/logs/EXPERIMENT-C-<timestamp>.log`)

Harness notes: (a) the original probe pointed at `/api/collections` which
answers 401 for guests before touching the DB — the probe was moved to a
DB-backed records route; (b) the lock must be released with
`pg_terminate_backend`, because `kill` on the `run_sql` subshell orphans the
`psql` and keeps the lock held.
