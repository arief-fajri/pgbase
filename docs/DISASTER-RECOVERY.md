## 1. Backup formats

A backup is a `.zip` under `pb_data/backups` (or S3). Format is `Backups.Format`:

| Format | Contents | Restore path |
|---|---|---|
| `pg` (default) | Native `pg_dump -Fc --no-owner --no-privileges` archive (`pgdata.dump`): entire DB — schema, record tables, `_params`, `_migrations`, `_superusers`, `_logs`, partitioned `_audits`/`_audit_reads`. Exact-replica DR snapshot | `pg_restore --clean --if-exists --no-owner --no-privileges` |
| `sqlite` (legacy, opt-in) | Portable v0.23-format `data.db`: records + schema + settings only (no request logs) | Normalized import |

Restore auto-detects (`pgdata.dump` → native, `data.db` → legacy). Requirements (native path): `pg_dump`/`pg_restore` on PATH, client major ≥ server major; overrides `PB_PG_DUMP_BIN`/`PB_PG_RESTORE_BIN` (validated); password via `PGPASSWORD`. Release image ships v16 client.

```bash
./pgbase backup                       # configured format, autogenerated name
./pgbase backup snap.zip
./pgbase restore snap.zip             # OFFLINE, no restart (restart after to load data)
```

Also via dashboard, `/api/backups` (superuser-only), autobackup cron (`Backups.Cron`, job `__pbAutoBackup__`) with count-based retention (`Backups.CronMaxKeep`, default 3). Creation bounded ~10 min; restore ~10 min; decompression capped by `PB_BACKUP_MAX_EXTRACT_BYTES` (8 GiB default, zip-slip + `LimitReader` guarded).

> **Trust boundary:** restore replays the archive (`pg_restore --clean`), i.e. executes arbitrary SQL from the dump. A tampered archive = DB takeover. Guard the bucket/filesystem like DB credentials.

## 2. Recovery targets

Targets are product-owned and must be validated by ongoing drills; the values below are the starting defaults (framework examples). Restore correctness of dump-based workflows was validated by experiment E (L3, 2026-09-12): backup → destroy schema → restore → schema/data/superuser intact — see record `evidence/experiments/EXPERIMENT-E-20260912-160628.md`. RPO/RTO numbers themselves are not yet drill-verified.

```text
RPO ≤ 15 minutes   (maximum acceptable data loss)
RTO ≤  1 hour      (maximum acceptable recovery time)
```

Dump-based workflows cannot hit a small RPO on large databases; PITR/WAL archiving (pgBackRest/WAL-G) is the path to tight RPO and is roadmap-open (Task 43).

## 3. Restore runbook (operator-executable)

1. **Stop** the app (restore is offline). Do not run alongside `serve`.
2. **Confirm** the archive: correct name, expected format, `pgdata.dump` vs `data.db`.
3. **Restore**: `./pgbase restore <name>` (or dashboard). Bounded to 10 min; failures report loudly.
4. **Verify (experiment E, L3)**: schema present; per-table counts match the source; settings sane; auth data intact; spot-check application reads.
5. **Restart** the app and confirm boot completes migrations cleanly.
6. **Record** the outcome in `evidence/` and update `last_verified_backup_timestamp`.

Recovery procedures must be executable by an operator who did not write the original feature (G-REL-05) — write them as step-by-step, not as notes.

## 4. Verification discipline

- A backup is **not valid** until a restore has been verified (G-REL-04, invariant I5).
- Restore success today is gated by a single `count(_collections) >= 1` check — **weak** (W-08). Hardening (per-table counts, expected schema, settings sanity) is roadmap Task 45; treat current restores as untrusted until experiment E passes the L3 checks.
- The meaningful operational signal is **`last_verified_backup_timestamp`**, not `last_backup_timestamp` — a created backup is not necessarily usable. This metric must be exported (gap, tracked in [OBSERVABILITY.md](./OBSERVABILITY.md#4-backup-and-recovery-metrics)).
- Backups should be stored **outside the application host** (S3 wiring exists; retention via `CronMaxKeep`).
